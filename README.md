# console —— 雪坡 · 手机阅读器（无后端、无依赖）

`index.html` 是 inline HTML / CSS / JavaScript 单页应用。浏览器用用户自己的令牌直接读写 Gitee / GitHub 私有仓；公开托管的页面与 Service Worker **只含空壳**，不附带正文、关注名单或凭据。

## 阅读与决策

> 2026-10-27 产品口径已由用户确认；以下为当前约定，不代表已线上发布。真机滚动、网络同步与跨设备场景尚待验证。

- 默认进入**干货**，可切换**水贴 / 收藏**，过滤为**默认（全部）/ 已读 / 未读**。
- **作者头行**：卡片开头是头像 + 作者名 + 平台 / 时间 / 已读，正文直接从第一段开始，不再用「作者：」前缀，也没有帖尾信息栏。
- **跨平台同文只出一条卡片**（ADR-0027）：同一个人在微博和雪球发同一篇时，平台标写 `雪球+微博`，评论两平台混排（先平台顺序再时间），每条带平台小标签（单平台不显示标签）；阅读 / 收藏 / 销毁 / 干货·水贴对整组生效（feed 的 `ids` 扇出），任一变体被销毁则整组隐藏。
- **评论进详情页**：时间线卡片不铺开评论，帖底「评论 N」键显示条数并进入帖子详情；点开是单独的帖子页（正文 + 引用 + 转发链 + 评论），顶部是 sticky 返回条（‹ + 头像 + 作者名 + ⋯）；返回恢复列表原位置，手机返回手势 / 浏览器返回也先回列表。评论 15px，比 18px 正文小一号。每条评论右上角另有 ⋯ 菜单：**复制**只复制评论文本；**删除**按「平台 + 作者 + 正文」哈希在本机永久隐藏该评论（旧的无平台哈希仍然认，评论计数同步下降），可立即撤销；**浏览器打开**跳到该评论所属平台的原文并把评论文字复制到剪贴板（两平台都没有单条评论的公开链接，做不到直接锚定）。
- **正文 18px / 行高 1.66、评论 15px、元信息 12.5px**，最大 760px 阅读宽度；手机整宽分行（无卡片圆角），≥600px 才回到卡片样式。
- **帖底四键对齐雪球 App**：分享 / 评论 N / 收藏 / ⋯ 更多。分享优先调系统分享面板（`navigator.share`，字段按浏览器能力从 `{title,text,url}` 逐级简化到 `{url}`，用户取消不算失败）；面板不可用时复制链接并说明「系统分享不可用」，再退化为把链接显示出来。收藏是切换按钮（星标填充）；改归属、销毁、浏览器打开收进「⋯ 更多」。
- **更多弹窗是底部小面板**：四个圆形图标按钮（复制、水贴 / 捞回干货、销毁、浏览器打开）+ 下方「取消」，点遮罩或按 Esc 关闭。选项与卡片动作同一套逻辑，仍走「取消确认就不改状态」。复制取正文 + 引用 + 转发链，走 Clipboard API，失败退到 `execCommand`，不弹阻塞式 prompt。
- **顶部只有一行**：视图（干货 / 水贴 / 收藏）+ 固定宽度的**三态同步标签**（可同步 / 同步中 / 已同步）+「⋯ 更多」。跳到某天、已读过滤、刷新信息流、投递清洗、全屏都收进「更多」菜单；日常没有保存按钮，也没有手动确认，三态始终占位、320px 也不隐藏。点标签打开同步详情（待同步字段 / 帖子 / 数据量、上次成功时间、同步策略档位、离线 / 授权 / 冲突原因、立即同步 / 重试、导出 / 恢复待同步）。详情页返回条也带同一个紧凑状态入口。
- **干货 → 水贴**、**水贴 → 捞回干货** 在帖底「⋯ 更多」里；收藏只在干货帖的动作栏提供，可取消，只标记，不等于归档；水贴的动作栏没有收藏（收藏视图只展示干货），因此是分享 / 评论 / 更多三键。各视图均无手动已读 / 未读按钮。移入水贴、捞回与收藏 / 取消收藏提供短暂的撤销提示；永久销毁不可撤销。
- 收藏视图只展示 **bucket=good 且 favorite=true** 的帖子；移入水贴保留收藏标记，但从收藏视图隐藏，捞回后重新出现。
- 水贴的**永久销毁**必须确认：该全局 id 在所有日期、所有视图中永不展示，不可恢复，也绝不勾选或新增投递。此操作存墓碑，不删除原始业务文件。后端渲染与手机推送也会剔除销毁正文；本机旧缓存可能仍含正文，但不会展示。
- **评论删除是本机状态**：只写 scope 内的 `hiddenComments` 缓存，不进 `reading_state` 同步；同一设备刷新 / 重开仍隐藏，换设备或清站点数据后会重新出现。复制帖子 / 评论不改变任何状态。
- 默认桶取 feed 的 `it.bucket`（`good` / `water`）；旧 feed 没有该字段时默认 `good`。旧 picks 只有**显式 `[ ]`** 会回落到水贴，缺失 id 或 `[x]` 不会把新 feed 的水贴变成干货。阅读状态中的显式 bucket 优先。

**历史 feed 只含过线干货，页面无法凭空补出水贴正文。需要桌面重新渲染该日期的 feed（以及 GitHub 数据面的推送），才可查看与回捞历史水贴。** 渲染不会重建或覆盖已有 picks。

### 跨日期阅读与收藏

- **干货 / 水贴**都是跨天、按发布时间倒序的时间线，不再按作者分块阅读。默认从最新日期开始；「跳到某天」以该日为起点，只向更早日期加载，不是只看当天。
- 首批以**当前视图与已读筛选下 20 条**为目标；逐日串行读取，每个日期整日加载，不在第 20 条截断当天。向下阅读时逐日懒加载，不并发预取全部历史。
- 连续空日扫描、收藏正文查找均**最多 7 天一轮**；到限额明确提示，可继续下一轮或暂停，不无限扫历史。加载失败停在原日期，提示重试；重试同日，不跳过缺口。
- **收藏**跨日期先展示作者列表，按作者最近一次收藏时间倒序；进入作者页后按帖子发布时间倒序。增量查找全局 favorite id 对应正文，而非只看当前日期或已加载帖；仅展示干货且未销毁的收藏。
- 尚未加载或查遍可用日期仍找不到收藏正文时，明确提示查找中 / 暂停 / 缺失，不把「未找到正文」假装成「零收藏」。干货、水贴、收藏分别保留浏览位置；收藏作者页返回时恢复作者列表位置。各视图的已读筛选独立，收藏不会继承干货的未读筛选。

### feed 时间与作者身份

新 feed 的作者组携带 `people.key`，帖子携带 `items.author_key`、`author_name`、`created_at`（epoch 秒）；稳定作者键用于跨日期归并，显示名用于展示，发布时间用于排序。旧 feed 回退到日期 + `time`（UTC+8）排序、显示名归组；新数据中显示名只对应唯一稳定键时可兼容归并旧名。同名或改名的旧 feed **不能可靠归并作者**，不宣称已解决身份关联。手机时间线的变化**不改 Markdown digest 按作者分组**。

### 已读

只有**帖尾 sentinel 完整进入视口并连续停留至少 1.5 秒，且页面在前台可见**才自动标记已读。首屏看到长文开头不会误标整篇已读；离开完整可见范围或切入后台中断计时，回来重新计时。移除手动已读 / 未读操作；不支持 IntersectionObserver 时使用 `scroll` / `resize` 检测帖尾完整可见，仍遵守同一计时条件，不回退到手动标记。

在未读视图中变为已读时，**当前卡片留在原处**，仅更新帖尾标记，不因过滤瞬移。明确切换视图 / 过滤、切日期或刷新后，重新应用过滤。

**收藏 / 取消收藏不打断阅读进度**：重排后用元素在文档里的坐标把「屏幕上方第一张可见卡」放回原位，不依赖重排前的 `scrollY`（浏览器会在换卡时把滚动位置夹回 0）。被移出列表的正是这张卡时，退回操作前的滚动位置，让下面的卡片上移补位。

### 自动同步与独立投递

1. 阅读 / 收藏 / 桶变化立即写本机 **outbox**（每个操作一条独立记录）。仅加载日期或自动已读 / 收藏不生成决策草稿；改变干货 / 水贴归属或销毁才产生相应日期的决策改动。
2. **自动同步是数据同步**：一轮批次里先写全局 `data/state/reading_state.json`，再把所有有待同步决策的日期自动写成 `daily/<date>/picks.md`（含固定 UTC+8 的 `# confirmed:` 与 `# decisions:` 决策摘要），**不再需要用户手动确认**。同一个写入锁内串行，不另开并发。
3. **频率按档位，且分决策 / 已读两组参数**（ADR-0026）：默认「省流」——决策类（桶 / 收藏）停手 45s 后同步 / 连续操作最长 600s / 80 个不同帖子提前触发 / 批次至少间隔 180s；已读标记单独更慢（停手 180s / 最长 1800s / 间隔 900s，不参与提前触发）。可选「标准」（15s / 180s / 30 帖 / 60s；已读 60s / 900s / 300s）与「及时」（3s / 15s / 10 帖 / 5s；已读 20s / 180s / 60s）。可在同步详情切换，按 scope 持久化。进后台只在有待同步决策时补一次（纯已读不抢跑）；失焦只排 2 秒短防抖且尊重批次间隔，`pagehide` 才强制；恢复前台 / 恢复网络时补一次，不承诺后台完成。
4. **数据量检测**：统计待同步字段数、帖子数，以及 `reading_state` 的原始字节与 base64 后请求体估算；超过约 800KB 自动拉长防抖（合并成更大批次），超过单批上限（约 1.5MB）则 fail-closed 停止写入并在详情说明，不盲写。详情持续显示上次同步的请求体大小与字段数。
5. **确认新鲜度**：`# decisions:` 只覆盖该日期的显式 bucket 值 + 桶时间戳（收藏 / 已读不影响）。自动同步后摘要与当前阅读状态一致；若另一台设备改了桶而本机还没重新同步，投递与桌面 `promote.py` 都会因摘要不匹配而要求先同步。旧格式 picks 没有摘要时，手机投递要求先触发一次自动同步，桌面归档保留兼容并警告。
6. **投递清洗**保持独立：提示明确列出**所选起始日期**，只针对该日期 feed；投递前会先自动同步待同步的筛选结果，失败则不投递。仅将该 feed 中已勾选干货写入 `data/state/clean_queue.json`，不投递水贴 / 销毁帖；重试按最新队列求并集，不覆盖他端新增项。

投递只是意图：桌面消费队列、生成归档骨架，后续仍需 Agent / 人做高保真清洗。**shadow_mode 与 `promote.py` 的摘要校验仍然生效**；页面不会关闭影子模式或调用 `--force`，收藏不绕过这些保护。

## 阅读状态与冲突协议

状态按 `wb:<id>` / `xq:<id>` 跨日期生效，写入所选私有仓：

```json
{
  "version": 1,
  "items": {
    "wb:123": {
      "bucket": "water",
      "bucket_updated_at": "2026-10-25T12:00:00.000Z",
      "favorite": true,
      "favorite_updated_at": "2026-10-25T11:00:00.000Z",
      "read_at": null,
      "read_updated_at": "2026-10-25T12:05:00.000Z"
    }
  }
}
```

每条只存在被改变的字段及其时间戳，不补默认值。独立合并 bucket、favorite、read_at，时间戳均为 ISO UTC；较新字段获胜，同时间戳取后者（与 `reading_state.py` 一致）。**destroyed 永远优先，已有墓碑不能恢复**。兼容历史显式未读状态仍使用 `read_at: null` 与新的 `read_updated_at`，不能靠删除字段表示；协议兼容不意味着页面保留手动未读入口。

每次写入 / 冲突重试重新读取远端，用最新远端与本机状态按字段合并后再 PUT，不能只换 sha 重传旧全文。远端解析采用 **fail-closed**：非法 root / items / id / 帖子状态 / 字段类型，或字段时间戳缺失、不是 ISO UTC，都拒绝整份状态并保留本机缓存提示；即使是缺时间戳的 destroyed 也不丢弃后写回。只有真实 404 视为文件缺失，API 失败或损坏 JSON 绝不当成空状态 PUT。未知字段忽略。picks 每次重试也重新 build：保留远端已有的非 feed 行与描述，patch 本机改过的 id / 显式阅读桶状态，并添加新 feed id（good 勾选，water / destroyed 不勾选）；销毁墓碑同时禁止旧行重新勾选。

- **Gitee**：手机直连主仓，状态与 picks / 队列写入该仓。
- **GitHub（推荐）**：手机只连私有数据面仓（例如 `davidsheh/spider-mobile`）；桌面 `scripts/mobile_sync.py` 的 pull / push 都会对全局 `reading_state.json` 双向字段合并，不限今天 / 昨天；push 会从 feed 剔除销毁正文。feed 由桌面推送，picks / 清洗队列由桌面拉回。后端 promote 允许人工回捞的 reject，但跳过 state bucket 为 water / destroyed 的条目。

### Gitee contents 接口的两个差异（真机踩过）

1. **不存在的路径返回 `200` + `[]`，不是 `404`**。把 `[]` 当文件读，`content` 就是 `undefined`，`atob('undefined')` 抛
   `The string to be decoded is not correctly encoded`。因此「文件缺失」必须是 `null` **或**数组（目录列表）。
   症状：`data/state/reading_state.json` 还没在仓库里时，每次开页都提示「阅读状态未取到」，
   保存决策也必然失败——而且它永远写不出去，形成死锁。
2. **新建文件用 `POST /contents/{path}`，`PUT` 只用于更新且要带 `sha`**（GitHub 两者都用 `PUT`）。
   首次写入 `reading_state.json` / `clean_queue.json` 时必须走 `POST`，否则更新接口返回失败。

客户端统一用 `fileEntry()` / `fileText()` 把「缺失」与「文件」分开，并在失败时给出明确错误，
绝不把 `undefined` / 非 base64 内容交给 `atob`，也绝不把 API 异常当成远端空文件覆盖。

## 离线与本机隔离

本机 localStorage 以 **provider / owner / repo / branch** 为 scope，保存 feed、picks、全局阅读状态、outbox 与同步策略。旧版不分仓的 `spider.feed.<date>` 缓存不会自动导入，避免串仓。

- 离线可读已缓存日期、自动标已读、操作收藏 / 桶；每个操作先落本机 outbox，失败不丢内存状态。有存储失败 / 离线 / 阻塞 / 字段冲突 / 数据量超限时顶部有持续说明（三态本身仍是「可同步」）。
- 刷新 / 跳转前暂存并提示；重新打开恢复 outbox 与缓存草稿，阅读入口默认最新，可明确跳到某天。离线 picks 读取失败不会当成空文件覆盖缓存。
- **自动同步**：联网且前台时按档位触发；请求统一 20s 超时，失败按 10 / 30 / 60 / 120 / 300 秒退避（限流优先 `Retry-After`），权限失败 / 远端损坏 / 校验失败 / 数据量超限会暂停并提示。切仓、登出、PIN 锁定会取消旧调度与代次，旧回调不写新 scope。多标签页用 Web Locks（不可用时退化为独立操作记录 + 广播 / storage 事件，并以远端 sha 冲突与幂等核对兜底）。
- **本机暂存失败**（配额不足 / 隐私模式 / 禁用存储）时保留内存状态但明确告警，并禁止销毁等高风险操作；可在同步详情导出 / 恢复待同步记录（不含令牌、PIN、正文）。旧版本 `readingDirty` 缓存会保守迁移为恢复批次，迁移中断可重放。
- PIN **只加密令牌**，不加密本机正文 / 状态缓存。请保护设备，勿公开业务文件或带凭据的输出。

## 安装与全屏

可将 `console/` 空壳单独部署到 HTTPS 静态站点（GitHub Pages、Netlify Drop、EdgeOne Pages 等），不要包含 `data/`、`daily/`、`archive/`。编辑源码本身不会发布，GitHub 一键发布命令见下节。

1. 打开空壳，选择 Gitee / GitHub，填写 `owner/repo`、可选分支及令牌。
2. 令牌：Gitee 请用**仓库级私人令牌**（令牌类型选「仓库级」，范围只勾数据仓，权限勾 `projects`；2026-11-01 起 Gitee 支持，早于此的判断见 ADR-0012 §7 的日期变更）；GitHub 用 fine-grained PAT，仅授权数据面私有仓 `Contents: Read and write`。两者都没有「只读」档位。
3. PIN 可选；留空明文保存在本机，设置后每次打开解锁。
4. 浏览器菜单 → **添加到主屏幕**，从主屏幕启动。

manifest 使用 `display: fullscreen`，`display_override: [fullscreen, standalone]`，保留 Apple web-app-capable。实际全屏能力取决于浏览器 / 系统，普通浏览器不能无交互强制全屏。「更多 → 全屏阅读」仅在用户点击时调用 requestFullscreen，失败会提示安装到主屏幕；**不开页请求全屏**。Apple 平台可能仍以 standalone 呈现。

也可直接传 `index.html` 到手机用 `file://` 打开（浏览器需允许 API 访问），但没有 SW / PWA 安装，换版需重传。HTTPS 下生产 SW 使用 **spider-shell-<内容版本>**，源码直接运行使用开发缓存；只缓存首页、manifest 与图标，API、同源业务文件和版本检查均不缓存。业务离线缓存只在按仓库隔离的 localStorage 中。

## GitHub Pages 一键发布

从 spider 仓库根目录执行；不用网页登录或 `gh` CLI。目标读取 `config.yaml` 的 `publish`
（本机覆盖同其他配置），默认 `DavidSheh/xuepo / main / root`。手机访问地址由「用户站自定义域名 +
本仓名」组成，即 `https://codebug.top/xuepo/`；改仓名就会改线上路径。

```yaml
publish:
  github_repo: "DavidSheh/xuepo"
  branch: "main"
  token_env: "SPIDER_PAGES_TOKEN"
  token_file: "~/.spider_pages_token"
```

在本机用户目录创建 `.spider_pages_token`（不是 `.txt`），UTF-8，仅一行实际 PAT。
Windows 路径通常为 `C:\Users\<用户名>\.spider_pages_token`。不把令牌写进 YAML、命令行、
手机页面或仓库。推荐 fine-grained PAT，仅选空壳仓、Contents 读写 + Pages 读写。
**这不是手机数据面的令牌，不要在手机填写它。**

凭据优先级：显式 `--token-file` > `SPIDER_PAGES_TOKEN` > 配置中的 token_file；不自动读取
`GITHUB_TOKEN` / `GH_TOKEN` / `~/.spider_gh_token`。首次准备令牌需要用户在 GitHub 创建，日常发布不需要浏览器登录。

```bash
python -B console/publish.py --dry-run  # 完全离线，不读 PAT；列文件、大小、版本
python -B console/publish.py --check    # 联网只读；检查来源、HTTPS、远端差异
python -B console/publish.py            # 真正写远端、请求构建并等待部署验证
```

发布仅上传五个源空壳文件，以及内存生成的 `release.json`、`.nojekyll`；不递归上传 console
目录，不上传 publish.py，更不上传任何业务数据或凭据。文件缺失、符号链接、疑似 PAT 都会阻止发布。
一次提交所有变化，保留远端其他文件；没变化不提交/不请求新构建，遇并发不强推。
不要求本地先 commit，不操作 spider 本地 Git，也不会提交已有暂存文件。

目标仓须已存在且公开、Pages 须是所配分支/root 来源。本工具不建仓、不改来源、域名或 HTTPS
开关。默认正式上传前必须验证实际站点的 HTTPS/TLS；证书错误、重定向或网络失败会停止。
若 Pages 未强制 HTTPS，会提醒手机只使用 HTTPS 链接；不能在公开 HTTP 页面中输入令牌。

若桌面无法连接站点（GitHub Pages 的 IP 在部分网络下不可达，这是常态），**直接显式**使用下列
模式，不需要也不应让人去手机上确认能否访问。它要求 GitHub API 的证书记录为 approved、未过期
且覆盖该域名，并且 URL 与 Pages 实际地址完全一致；不会关闭 API 的 TLS 验证。
不能把 HTTP 地址或其他站点的地址拿来跳过默认预检，也不能不传 URL 就隐式跳过站点核对。
`--confirmed-https-url` 是旧参数名，仍可用，但不再含「已确认」之意。

```bash
# 先只读检查，再发布；URL 必须与 Pages 实际 HTTPS 地址完全一致
python -B console/publish.py --check --api-only --https-url https://codebug.top/xuepo/
python -B console/publish.py --api-only --https-url https://codebug.top/xuepo/
```

该模式只确认目标提交的 Pages 构建完成，**不会声称桌面站点连接或线上 HTML/SW 验证成功**
（输出会写明「桌面站点连接与线上文件未验证」）。默认命令依旧要求桌面 HTTPS 实际探测；
此模式不能自动启用，也不能存成常驻默认配置。

默认等待 180 秒轮询目标提交的构建（单个网络请求最多 20 秒 socket 超时；DNS/网络可能使总时长更长）。
`--timeout 300` 可延长轮询等待；`--no-wait` 只是不等构建，不能据此认为已部署。
成功需构建提交匹配，且线上 release/HTML/SW 与本次版本一致。提交后构建失败或超时会明确提示，
先检查不要盲目重复发布。

版本按内容生成，不随发布时间或 Windows 换行变化。发布自动生成生产缓存版本；手机在「更多」
查看版本并检测更新，新版只提示，刷新必须手动触发。未确认选择、未同步阅读状态、其他日期草稿、
同步进行中或本机存储异常时不能刷新。新版本不会自动删除本机业务缓存。
旧 v2 页面没有新版检测逻辑，第一次升级可能需要先处理草稿再手动刷新；之后才有新版提示。
HTTP 与 HTTPS 的本机存储互相隔离，若原先使用 HTTP，请先妥善处理旧页面草稿，不能假定它们
自动出现在 HTTPS 中。不要在 HTTP 页面输入令牌。
